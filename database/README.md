# SIH26190 Supabase PostgreSQL database

This folder owns the PostgreSQL application store for SIH26190. It stores user
authentication data, document metadata and file references, version metadata,
and a local cache of access logs. Blockchain state remains authoritative for
document integrity and access history.

## Supabase connection

The hosted application database is Supabase Postgres. For an IPv4 application
server, use the project's session-pooler URI (port 5432) as `DATABASE_URL`, set
`DB_SSL=true`, and keep `DB_SSL_REJECT_UNAUTHORIZED=false`. The local `.env` is
ignored by Git and must never be committed.

The dashboard SQL editor owns hosted schema migrations. Set
`DB_AUTO_MIGRATE=false` for the restricted runtime role so application startup
does not require schema-owner privileges. To apply a new hosted migration, run
the reviewed SQL in Supabase first and record its filename in
`public.schema_migrations`.

## Run the connected frontend locally (no Docker required)

Install dependencies once, from this `database` folder:

```sh
npm ci
npm ci --prefix ../backend
npm ci --prefix ../frontend
```

Then start PostgreSQL, the existing backend API, and the frontend together:

```sh
npm run dev:local
```

Open **http://127.0.0.1:5173/** and sign in with **admin1 / pass123** (or one
of the accounts below). The old frontend-only `admin / admin123` login has been
removed. The first local start initializes and seeds the database. Later starts
reuse its saved records. Stop with Ctrl+C. PostgreSQL data remains in
`database/.local-postgres/`; uploaded files remain in `database/uploads/`.

This optional development runtime uses the `embedded-postgres` package. It binds
PostgreSQL and the app to loopback. It is not a production database deployment.
Do not run it alongside another PostgreSQL instance on the same port. If one is
already running, use the existing-database instructions below instead.

The UI now uses API requests for sign-in, documents, uploads, verification,
document details and history. Refreshing the page reloads saved records. Empty
databases show an empty dashboard, never fabricated documents or metrics.
The frontend keeps its token in session storage, validates it through `/auth/me`,
and returns to sign-in when the API rejects the session.

**Blockchain remains required for successful uploads and verification.** Set
`BLOCKCHAIN_RPC_URL` and `BLOCKCHAIN_PRIVATE_KEY` in `database/.env`, and ensure
`backend/shared/DocumentRegistry.json` matches a deployed contract whose writer
role is granted to that key. Without it, login and database reads work, but
uploads fail explicitly and verification stays pending. No simulated blockchain
results are used by the running application. AI analysis remains optional; an
unavailable AI service flags documents for review.

## Use Docker or an existing PostgreSQL database

From this `database` folder, start PostgreSQL with one command:

```sh
docker compose up -d
```

On the first start, Docker automatically runs the schema migration and demo-user
seed. The local connection string is:

```text
postgresql://sih_user:sih_password@localhost:5432/sih26190
```

Copy `.env.example` to `.env` when running the Node scripts or client directly.
For an existing database (or after adding a future migration), run:

```sh
npm install
npm run db:setup
npm run dev
```

Stop the container with `docker compose down`. Its named volume preserves data.
Use `docker compose down -v` only when you intentionally want to erase the local
database and rerun first-start initialization.

## How the integration works

`src/server.js` is an alternative entry point for the **existing** backend route
modules. It loads configuration from `database/.env`, applies migrations, and
mounts `backend/src/routes/auth.js` and `backend/src/routes/documents.js` without
modifying backend files. Start it alone with `npm start`, or start it alongside
Vite with `npm run dev`.

Migration `002_backend_compatibility.sql` adds writable views in the
`backend_api` schema. The API pool uses `search_path=backend_api,public`, so its
camelCase SQL reads/writes the same records as the canonical snake_case tables.
No records are copied. Foreign keys and append-only version triggers still apply.
Migrations, seeding and the reusable database client use the canonical tables.
Do not run the old `backend/src/app.js` startup against this schema: its table
creation and startup seed target the old schema. Use the database launcher.

`vite.config.mjs` serves the existing frontend and proxies `/api` to port 5000
(or `PORT`). `browser/api.mjs` is a browser-safe client with no database secrets.
The only source file changed outside this folder is `frontend/src/main.jsx`:
the UI must make API requests to replace its previous in-memory demo behavior.
Use `npm run dev` from **this folder**, not the original frontend-only command,
to get the API proxy.

The launcher adds `GET /api/auth/me` for session validation and
`GET /api/document-metadata` for saved hashes, uploader names and AI risk flags.
The existing backend routes handle login, listing, upload, detail, version,
verification and blockchain history. Missing file sizes are shown as unavailable.
The original simulated download action is omitted because there is no download
API. Blockchain failures are displayed rather than converted to success.

## Reusable database client

For new server-side code that uses the canonical snake_case schema, import:

```js
const db = require('./src'); // relative to database/
```

Query it normally:

```js
const result = await db.query(
  'SELECT user_id, username, password_hash, role FROM users WHERE username = $1',
  [username],
);
```

Exports are `pool`, `query(text, params)`, `getClient()`,
`transaction(callback)`, and `close()`. `transaction` passes a checked-out
`pg` client to the callback and handles commit, rollback, and release.

Set `DATABASE_URL` for your PostgreSQL connection. The API listens on port 5000;
PostgreSQL listens on port 5432. The browser talks only to the authenticated API.

## Exact schema contract

### `users`

| Column | Definition |
| --- | --- |
| `user_id` | UUID primary key, defaults to `gen_random_uuid()` |
| `username` | text, unique, not null |
| `password_hash` | text, not null |
| `role` | text, not null; `investigator`, `court_clerk`, or `admin` |
| `created_at` | timestamptz, not null, defaults to `now()` |

### `documents`

| Column | Definition |
| --- | --- |
| `doc_id` | UUID primary key, defaults to `gen_random_uuid()` |
| `filename` | text, not null |
| `filepath` | text, not null |
| `doc_hash` | text, not null; SHA-256 hexadecimal value |
| `uploader_id` | UUID, not null; references `users(user_id)` with `ON DELETE RESTRICT` |
| `current_version` | integer, not null, defaults to 1 |
| `ai_risk_flag` | text; `clean` or `review_recommended` |
| `status` | text; `verified`, `tampered`, or `pending`; defaults to `pending` |
| `created_at` | timestamptz, not null, defaults to `now()` |
| `updated_at` | timestamptz, not null, defaults to `now()` and updates automatically |

### `document_versions`

| Column | Definition |
| --- | --- |
| `version_id` | UUID primary key, defaults to `gen_random_uuid()` |
| `doc_id` | UUID, not null; references `documents(doc_id)` with `ON DELETE RESTRICT` |
| `version_number` | integer, not null; unique within one document |
| `doc_hash` | text, not null; this version's SHA-256 hexadecimal value |
| `filepath` | text, not null; old version files must never be overwritten or deleted |
| `reason` | text, nullable |
| `updated_by` | UUID; references `users(user_id)` with `ON DELETE RESTRICT` |
| `created_at` | timestamptz, not null, defaults to `now()` |

This table is append-only at the database level: a trigger rejects `UPDATE` and
`DELETE`, so corrections must create a new version instead of changing history.

### `access_log_cache`

| Column | Definition |
| --- | --- |
| `log_id` | UUID primary key, defaults to `gen_random_uuid()` |
| `doc_id` | UUID, not null; references `documents(doc_id)` with `ON DELETE RESTRICT` |
| `user_id` | UUID, not null; references `users(user_id)` with `ON DELETE RESTRICT` |
| `action` | text; `view`, `download`, `share`, `verify`, or `upload` |
| `tx_hash` | text; matching blockchain transaction hash, when available |
| `created_at` | timestamptz, not null, defaults to `now()` |

Indexes exist on `documents(doc_hash)`, `documents(uploader_id)`,
`document_versions(doc_id)`, and `access_log_cache(doc_id)`.

## `doc_id` consistency rule

Generate a document UUID exactly once in the backend upload handler. Pass that
same value to both:

1. `INSERT INTO documents (doc_id, ...) VALUES ($1, ...)`
2. the smart contract's `registerDocument(docId, ...)` call

Although the database default is useful for manual records, the upload flow must
not independently generate one UUID in PostgreSQL and another in application or
blockchain code.

## Checks and builds

```sh
npm run check
npm test
npm run build
```

Tests create a separate local PostgreSQL cluster on port 55432 and a uniquely
named test database, which is dropped afterward. They never connect to your
configured application database. Tests exercise actual SQL migrations, bcrypt
login, JWT protection, upload persistence, version history and tamper detection.
Successful blockchain responses are test doubles; the unavailable-chain test
checks that uploads fail without saving data. Application code has no test bypass.

The production frontend build is written to `database/dist/`. When serving it
separately, set `VITE_API_URL` to the API's full URL ending in `/api` at build
time, or configure a same-origin `/api` proxy. Set `FRONTEND_ORIGIN` on the API
to the deployed frontend origin, `HOST=0.0.0.0` when required by the hosting
platform, and a long random `JWT_SECRET`. Keep all database and blockchain
credentials server-side. Use a hosted PostgreSQL database and persistent upload
storage for deployment. Without `JWT_SECRET` in local development, a temporary
secret is generated at startup, so restarting the API requires signing in again.

These migrations expect the canonical schema above. If a database was already
created with the old backend's camelCase tables, migrate that existing schema
with a reviewed data migration before connecting it; do not drop its tables.
